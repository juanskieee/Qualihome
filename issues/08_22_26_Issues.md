### 5. TCP / Pricing Fields – Add Comma Formatting

**Issue:**
Number fields for pricing (Total Selling Price, Reservation Fee, Downpayment, etc.) do not format numbers with commas as the user types.

**Fix:**
- Add **comma formatting every 3 digits** (e.g., `8,693,774.02`) on all currency/pricing input fields as the user types.
- Apply this to: Total Selling Price, Reservation Fee, Downpayment %, Downpayment Terms, Loanable Percentage, and **any other field involving peso amounts**.
- Use a number formatter or input masking library (e.g., `Intl.NumberFormat`, `cleave.js`, or `imask`).

### 7. Peso Sign – Fix Missing/Broken Currency Symbol

**Fix:**

- Audit all price display components across the admin panel for this issue.

## 🎨 GLOBAL STYLING RULE — APPLIES TO ALL CHANGES

> ⚠️ **This rule is mandatory for every single fix, feature, or UI change in this document.**

All changes — whether new components, modified forms, reordered fields, new labels, modals, or any UI element — **must strictly follow the existing project's design system**. Do not introduce new styles, utility classes, or design decisions that are not already present in the codebase.

### What to check before writing any new UI code:

1. **CSS Variables / Design Tokens**
   - Read the project's `:root` CSS variables (e.g., `--primary-color`, `--font-size-base`, `--border-radius`, `--spacing-*`, etc.) before applying any color, size, or spacing.
   - Never hardcode hex colors, pixel values, or font sizes — always use the existing CSS custom properties.

2. **Existing Component Styles**
   - Before creating a new input, button, modal, dropdown, or label — find how the same element is already styled elsewhere in the project and replicate that exact pattern.
   - Example: if the existing delete button uses class `btn-danger` or a specific Tailwind/CSS class combo, use the same for any new delete button.

3. **Typography**
   - Match the font family, weight, and size already used in similar UI contexts (form labels, card text, table headers, etc.).
   - Do not import new fonts.

4. **Spacing & Layout**
   - Use the same margin, padding, and gap values as surrounding elements in the same section/component.
   - Follow the existing grid or flex layout patterns used in forms and cards.

5. **Modal / Dialog Styling**
   - Any new or modified modal (e.g., confirmation dialogs, Add forms) must use the same modal wrapper, header style, footer button layout, and overlay as existing modals in the project.

6. **Form Field Styling**
   - New, merged, or reordered fields must use the same input class, icon placement style, label color (e.g., the red/maroon label color visible in the screenshots), and field sizing as existing form fields.

7. **Color Palette**
   - The project uses a **dark maroon/red primary** (`#7B1A1A` range) for headers, active states, and buttons.
   - Accent labels and required field markers use a similar red tone.
   - Success/availability uses green. Do not deviate from these.

8. **Icons**
   - Use the same icon library and style already in use (visible icons in screenshots suggest a custom icon set or a library like FontAwesome/Heroicons). Match existing icon usage — do not mix icon libraries.

### In practice — before every change, ask:

```
- What CSS variables does this project define in :root?
- What class names are already used on similar elements?
- What does the existing modal/form/button look like, and how is it built?
- Am I introducing anything (color, font, spacing, component) not already in the codebase?
```

If yes to the last question — **stop and align first**.
